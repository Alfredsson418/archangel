# Current Security Concerns

This document summarizes security limitations visible in the current Archangel implementation and deployment configuration, reviewed on 2026-11-01. It is a living status document, not a penetration-test report, vulnerability disclosure, compliance claim, or complete threat assessment. Risk labels are relative priorities for addressing the concerns, not CVSS ratings.

## At a Glance

| Priority | Current concern | Current status |
| --- | --- | --- |
| Medium | Dashboard account administration is API-only | Backend account lifecycle operations are available through administrator-only APIs; no dashboard account-management UI exists yet. |
| High | Unprotected network transport | The C++ API serves plain HTTP; the project does not configure TLS termination. |
| High | Privileged, immediate firewall changes | Rule changes take effect immediately; dashboard bundle imports consist of separate, non-atomic API calls. CLI config import uses nftables transactions but remains privileged. |
| Medium | Log confidentiality and audit limitations | The authenticated logs endpoint exposes bounded application and packet logs; redaction is partial. |
| Medium | Availability controls and verification gaps | Login, API-request, and firewall-mutation limits are implemented with in-memory fixed windows; counters reset on restart. Automated C++ unit tests cover selected parsing and HTTP-handler behavior but do not constitute broad integration, fuzz, or security testing. |
| Medium | Session and deployment configuration | Production requires a stable `FLASK_SECRET_KEY`; the cookie's Secure flag is operator-configurable and defaults off for loopback HTTP. |

These priorities assume the API or dashboard can be reached by an untrusted party. Binding to localhost reduces network exposure but does not add authentication and is not sufficient for a deployment that intentionally exposes either service to a network.

## Current Concerns

### 1. Authentication and account-management boundaries — Medium

The C++ API now validates a backend-issued Bearer session before dispatching every route by default. Only bodyless `GET /status/health`, `POST /api/v1/auth/login`, and one-time `POST /api/v1/auth/setup` are public. The login endpoint issues opaque sessions; logout revokes them. Authenticated viewers may read endpoints, `POST /api/v1/rules` and `DELETE /api/v1/rules` require an operator or administrator role, and account-management routes require an administrator. The API schema header still only versions the contract and is not an access control.

The Flask dashboard now provides a backend-backed login flow. It stores the opaque backend credential in an owner-only server-side SQLite session store and includes it on protected API calls; the dashboard does not maintain a separate user database. The backend remains the authority for identity and permissions. A frontend login alone must not grant API access; each backend request must carry the backend-issued session. Keep both services on localhost or an isolated, trusted management network, including traffic between separate computers. Do not expose either service to the public internet.

The liveness endpoint `GET /status/health` is intentionally public and returns no response body. The login endpoint is public so clients can obtain sessions, and one-time `POST /api/v1/auth/setup` is public so an administrator-issued setup token can be redeemed; keep this allowlist explicit and narrow.

The backend uses the local SQLite/Argon2id `AuthProvider` for credential verification and opaque API-session storage. Sessions are revocable and expire based on idle and absolute timeouts. Initial administrator provisioning remains an interactive CLI operation. Login attempts are limited per source IP in bounded in-memory state; counters reset on process restart. General API requests are limited per source IP and authenticated identity, and firewall mutations have an additional limit per source IP and identity. These bounded fixed-window counters reset on process restart.

### 2. Network traffic is not protected by project-configured TLS — High

The C++ service uses a plain HTTP server. The dashboard API base URL is fixed by deployment configuration; it does not provide TLS for the C++ service. The supplied same-host Compose setup uses host networking and loopback defaults; separate-host operation requires explicit network configuration and has no built-in encrypted API transport.

On an untrusted network, requests and responses can be observed or modified in transit. This is especially serious because API requests can change firewall rules. Keep service-to-service and browser-to-dashboard traffic on localhost or a trusted, isolated management network until an appropriate TLS deployment is available. HTTPS at a reverse proxy, if independently configured by an operator, is not configured or guaranteed by this repository.

### 3. Dashboard session and API destination configuration — Medium

The API destination is fixed at startup through deployment configuration and cannot be changed through the browser, preventing a browser user from redirecting backend-held credentials. Keep the configured destination limited to the intended backend and trusted management network.

All state-changing dashboard requests require a session-bound CSRF token and validate the supplied Origin when present. These browser protections complement, but do not replace, backend authentication and authorization.

The browser session cookie is `HttpOnly` and `SameSite=Lax`. Production startup requires `FLASK_SECRET_KEY`; development mode may use an ephemeral key that invalidates sessions on restart. The `Secure` cookie flag is configurable and must be enabled when dashboard HTTPS is provided by an operator-managed reverse proxy. Session payloads are stored in SQLite with an owner-only directory and database file.

### 4. Firewall changes have immediate host impact — High

The C++ backend can add and delete active firewall rules. The effective operating-system privileges depend on how the binary is launched, but it must have sufficient privilege to perform its firewall operations. Compromise or misuse of an API process with those privileges can affect host or network availability. Run the backend with only the privileges it needs and protect its host and management network.

Rule updates take effect immediately and are not automatically rolled back. The dashboard portable-rules importer validates and previews the bundle, then submits rules individually. If a later request fails, earlier rules remain applied; there is no batch transaction or rollback. Its export omits rules that the structured API cannot represent.

The backend CLI exports and imports version 1 firewall config bundles containing the complete active nftables ruleset but no listener settings. Firewall bundle v1 uses the `archangel-firewall-config` format and separates rules bearing the reserved `archangel-managed` nftables comment from other rules and objects. `--firewall-rules-mode replace` atomically replaces marked rules only, leaving external rules and objects untouched; referenced tables and chains must already exist. `--firewall-rules-mode replace-all` explicitly flushes the entire active ruleset and may disconnect clients or lock out administrators. Review imported files and confirm recovery access before using full replacement. The ownership comment is a categorization marker, not an authentication or authorization control. Neither the dashboard bundle nor the CLI firewall config is automatically restored after reboot unless an operator configures the startup command or service accordingly.

The System Management page is currently read-only. It does not restart or otherwise control the host.

### 5. Logs may reveal sensitive information; redaction is limited — Medium

The authenticated `/api/v1/logs` endpoint exposes recent Archangel application-log entries and, when configured rules generate packet logs, recent matching kernel-journal entries. These can reveal host details, network addresses, and operational behavior. The backend bounds the returned entries and applies pattern-based redaction to common credential-like fields, but this is not comprehensive secret detection and must not be treated as a confidentiality boundary.

The current API request logs record method, fixed path, status, duration, and some operation outcomes, but do not attribute requests to verified identities. No tamper-resistant audit-log storage or retention policy is implemented. Do not place credentials or secrets in log messages; restrict log and dashboard access as carefully as other host information.

### 6. Denial-of-service and security verification controls are incomplete — Medium

The API applies bounded per-source-IP and per-identity request limits, plus per-source-IP and per-identity firewall-mutation limits. These fixed-window counters reset on restart and do not provide a general capacity guarantee. No security or capacity guarantee should be inferred from the liveness endpoint.

The dashboard unittest suite and `make test` provide automated coverage for selected frontend behavior, config parsing/serialization, nftables statistics parsing, and API handlers. They do not provide broad integration, fuzz, authorization, or live nftables tests. Ordinary tests must remain isolated from privileged host firewall state; security-sensitive changes need focused tests and an appropriate non-production integration environment.

### 7. Listener exposure depends on deployment configuration

The C++ API defaults to `localhost:8080`, and the Flask development entry point defaults to `127.0.0.1:8081`; these defaults reduce remote exposure on a single host. Dashboard routes require an authenticated browser session; backend authorization remains independently enforced for each protected API request. Both services can be configured differently. The supplied Compose file uses host networking with a loopback dashboard bind. Changing bind addresses, publishing ports, adding a reverse proxy, or deploying the services on separate hosts changes the reachable attack surface and must be reviewed before use.

The portable-dashboard deployment model is intentional, but portability does not itself make remote connections safe. The dashboard now integrates backend login, but the API has no project-configured encrypted transport. A remotely deployed dashboard must only reach its intended backend over a trusted management network.

## Planned Security Work

The following list distinguishes implemented controls from remaining work.

- **Implemented:** the backend-owned `AuthProvider` interface and SQLite local provider use Argon2id, create UUID account IDs and opaque sessions, store password hashes and only SHA-256 session-token hashes, and require a private service-owned database directory/file. `user bootstrap-admin` is an interactive TTY-only command that creates an administrator only if one is not already enabled. Global API middleware authenticates every route except bodyless health, login, and one-time account setup; firewall mutations require Operator or Administrator, and account-management routes require Administrator. Login attempts and API/firewall-mutation requests are rate-limited.
- **Still planned:** provide a backend `user recover` command that may bypass API last-admin safeguards and retain OIDC as a future provider option. Administrator API account creation, listing, updates, disablement, setup/reset tokens, immutable IDs, and last-administrator protections are implemented; no separate frontend identity store is used.
- Administrator-only backend account APIs issue single-use setup tokens for account creation and password reset; no dashboard account-management UI exists yet. Store only token hashes, never log tokens, and require the account holder to set their own password.
- Setup tokens expire after one hour; allow only one outstanding token per account. New accounts remain pending until password setup completes. Only administrators initiate resets; reset initiation revokes sessions and invalidates prior tokens. Disabled accounts cannot redeem tokens; after setup the user performs a normal login.
- **Implemented:** password hashes use the Argon2id baseline (19 MiB memory, 2 iterations, parallelism 1), with encoded parameters stored in SQLite. Runtime config may increase the parameters within documented resource bounds, and administrator bootstrap consumes the configured values. **Still planned:** rehash after successful authentication when configured cost increases; benchmark stronger settings to avoid login-driven availability issues.
- Store local accounts, opaque API sessions, and schema metadata in a runtime-configurable SQLite database, default `/var/lib/archangel/archangel.db`. Require a service-owned parent directory with mode `0700` and DB file mode `0600`; fail if unsafe. Use SQLite online backup or stop the service before copying; version migrations and fail startup if migration fails.
- **Implemented:** require 15–128 Unicode code points for passwords and reject invalid UTF-8 or oversized input. **Still planned:** reject known common/compromised passwords where feasible; avoid arbitrary composition rules or forced periodic rotation.
- Require only username and password; do not require email, phone, or other personal data. Assign immutable random UUID user IDs. Usernames use ASCII letters/digits plus `._-`, 3–64 characters, are case-insensitive and normalized, and cannot be reused after disablement. Use generic login failures for unknown, disabled, and incorrect-password accounts and perform dummy Argon2id verification for nonexistent users. Initial authentication is password-only; MFA is deferred and password compromise remains a residual risk.
- **Implemented:** backend-enforced `viewer`, `operator`, and `administrator` roles. Viewers can read protected API endpoints; operators can also change firewall rules; administrators can manage accounts. Deny by default. Keep `GET /status/health`, the narrowly scoped login route, and one-time setup-token redemption as the only public routes.
- Use a Flask backend-for-frontend flow with a 256-bit CSPRNG opaque API session token returned only at login; store only its SHA-256 hash in the private backend SQLite DB and never log it. Keep the token in `/data/sessions.db` (configurable) in a dedicated server-side SQLite browser-session store on the dashboard host. This store contains session credentials only, not identities or password hashes, and requires an owner-only directory and database file. Loss invalidates browser sessions and requires reauthentication; no session DB backup is required. Backend session lifetimes are configurable, initially 15 minutes idle and 8 hours absolute, and sessions are revoked on logout or account/security changes. Authenticate and authorize each protected API request independently.
- Protect dashboard sessions with an opaque `HttpOnly`, `SameSite=Lax` cookie; enable `Secure` when served behind operator-managed HTTPS, but keep it off for default loopback HTTP. Rotate the browser session ID after login and privilege changes. Require CSRF tokens on every state-changing dashboard form, including login/logout, settings, and account management; validate `Origin` where available. Keep the cookie/session signing key in a protected file or environment variable, not config/source; production startup fails if absent, while local development may use an ephemeral key that invalidates sessions on restart.
- Add optional native TLS for the C++ API, disabled by default for local development, with operator-provisioned certificate/key paths in backend runtime config. Require TLS 1.2 or newer; when enabled, missing or invalid cert/key files fail startup rather than falling back to HTTP. The private key is readable only by the backend service account. Certificates load at startup; operator restarts the backend after renewal. The dashboard validates hostname and certificate using system trust plus an optional private CA bundle selected by a deployment environment variable such as `ARCHANGEL_API_CA_BUNDLE` pointing to a read-only-mounted PEM file; verification cannot be disabled. Recommend enabling TLS in production. Keep the dashboard loopback-bound by default; remote browser access requires operator-managed reverse-proxy HTTPS.
- **Implemented warning; still unsafe:** the backend logs a prominent startup warning when bound to a non-loopback address without TLS. This remains plaintext and exposes credentials and API traffic to network interception/modification; it is not a secure production configuration.
- **Implemented:** login-attempt limits default to 5 failures per source IP per 5 minutes, API limits to 120 requests per minute per source IP and authenticated identity, and firewall-mutation limits to 30 per minute per source IP and identity. Bounded, thread-safe fixed-window limiters return HTTP `429` with `Retry-After` and reset on restart. They use the direct peer IP, ignore forwarded headers, and exempt health.
- **Partially implemented:** the separate v1 JSON runtime config (`format: "archangel-runtime-config"`) has strict schema/value validation and a protected-file loader. It checks regular-file type, root/service ownership, group/world write bits, and rejects final-component symlinks. The implicit `/etc/archangel/config.json` may be absent; explicit `--config PATH` is required. Bind settings and bootstrap database/password/Argon2id settings are consumed. Firewall import/export stays separate and explicit.
- **Implemented:** runtime session, login-attempt, API-request, and firewall-mutation limit settings are connected to the API. TLS cannot currently be enabled and configurable logging remains unimplemented; unsupported non-default settings fail startup instead of appearing effective. The dashboard login integration is implemented.
- Add replaceable logging backends to both services. Start with separate configurable JSONL append files: backend default `/var/log/archangel/backend.jsonl`, dashboard default `/data/archangel-frontend.jsonl`. Include timestamp, level, service, event, actor ID when known, operation, outcome, request ID, and source IP on every request. Never log credentials, request/response bodies, submitted values, or raw rules. IPs are privacy-sensitive; restrict access and retain compressed rotations for 30 days by default, configurable by operators. Require owner-only access and OS-managed rotation; reopen safely on rotation without `copytruncate`. Consider journald/syslog or a protected append-only sink as future adapters. Ordinary append files are not tamper-evident.
- If a configured log sink cannot open at startup, fail startup. At runtime, log-write failures emit sanitized stderr diagnostics, block protected/mutating operations, and leave only bodyless health available until recovery. Require the audit intent event before privileged mutation; outcome logging can still fail after an already-completed operation, which cannot be rolled back.
- Complete the threat model and CIA/IAAA assessment, including operational dependencies and residual risks. The local provider avoids a mandatory external identity-service dependency; TLS certificate failures, rate limits, file-log alteration, privileged misuse, and added provider/sink abstractions remain relevant risks.
- OIDC claim-to-role mapping remains deferred until OIDC is selected for implementation. MFA is deferred; the initial design uses username/password only.
- Dashboard session protections are selected: CSRF tokens on all state-changing forms, session rotation, and secure cookie configuration when HTTPS is used. Fix the API destination at deployment through `ARCHANGEL_API_URL`; do not allow browser users to edit it, which could redirect backend-held credentials to an arbitrary host. Enforce the approved security policy without allowing TLS-verification bypass.
- Expand the automated C++ unit tests and add appropriate security-focused checks without allowing ordinary tests to alter a live firewall.

The [security-control roadmap](roadmap.md#phase-2-backend-owned-security-controls) tracks the planned backend-owned authentication, HTTPS, and rate-limiting work. Design choices that affect identity, credentials, trust boundaries, or deployment should be decided before implementation.

## Design Principles

Security controls should be proportionate to the threats they address. New components can add attack surface, configuration hazards, and maintenance burden; complexity can itself increase risk. Prefer the simplest effective control, state residual risk, and consider operational recovery and availability as well as access prevention.

The thesis [Zero Trust i isolerade komplexa miljöer](../assets/Zero_Trust_i_Komplexa_Isolerade_Miljöer.pdf) provides long-term architectural context, including mutually authenticated gateway links, policy decision and enforcement points, microsegmentation, session review, and protected security logging. Those ideas are not current controls or evidence of compliance. Any future design must account for availability, recovery, key and certificate lifecycle, control-plane protection, and log integrity.
